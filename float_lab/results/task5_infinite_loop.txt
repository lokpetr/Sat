=== 5. Бесконечный цикл на float-счётчике ===

расстояние между соседними float (ulp) вокруг степеней двойки:
     k        float 2^k          ulp = шаг сетки      1.0f < ulp ?
   2^18            262144.0           0.03125            нет
   2^19            524288.0            0.0625            нет
   2^20           1048576.0             0.125            нет
   2^21           2097152.0              0.25            нет
   2^22           4194304.0               0.5            нет
   2^23           8388608.0                 1            нет
   2^24          16777216.0                 2            ДА -> шаг теряется
   2^25          33554432.0                 4            ДА -> шаг теряется
   2^26          67108864.0                 8            ДА -> шаг теряется

  при x >= 2^24 = 16777216 шаг сетки уже 2, то есть +1.0f физически некуда применить:
  x + 1.0f округляется обратно к x. Значит цикл вида
      for (float x = 0; x < 1e30f; x += 1.0f) { ... }
  застрянет насовсем (1e30 -- это сильно больше 2^24, предела не дождёмся).


  где происходит то же самое, только с другим форматом (критерий тот же:
  шаг 1.0 перестаёт помещаться между соседними числами):
  формат        значащих бит   1.0 теряется с   max<T>          comment
  float              24         2^24       3.403e+38   SSE2, -O2 по умолчанию
  double             53         2^53       1.798e+308   SSE2
  long double        64         2^64       1.190e+4932  80-битный x87 = то, на чём считают
                                             без -msse2 (32-битные
                                             сборки, -m32)
  (до 2^64 досчитывать, конечно, никто не стал: это ~360 лет на этой машине при
   836 млн итераций/с; здесь границу даёт то же сравнение ulp, что и выше)
  #iter        x          x+1.0f (то же?)     скорость, млн ит/с   время
    4194304           4194304.0   нет          1078.7          0.00 s
    8388608           8388608.0   нет          1036.6          0.01 s
   12582912          12582912.0   нет          1104.5          0.01 s
   16777216          16777216.0   ДА, не меняется!          1017.8          0.02 s
   20971520          16777216.0   ДА, не меняется!           779.7          0.02 s

  >>> ЦИКЛ ЗАСТРЯЛ на x = 16777216.000000000  (= 2^24)  после 20971521 итераций за 0.0212 с
      следующий float после x : 16777218.0000  (расстояние 2.0000, наш шаг 1.0f в 2 раза меньше)
      x + 1.0f = 16777216.000000000  -- то же самое число, поэтому условие
      x < 1.000000015e+30 никогда не станет ложным.

  то же самое на double застряло бы на 2^53 = 9007199254740992,
      при измеренной скорости 987.6 млн итераций/с это ~105.6 суток непрерывной работы
      (и это БЕЗ учёта тела цикла). Вывод: 'перейти на double' -- не исправление бага,
      а просто отсрочка аварии на месяц-другой.
      На 80-битных x87-регистрах (старые 32-битные сборки) граница ещё дальше:
      2^64, то есть цикл 'работает' -- и это как раз пример рецепта, который
      перестаёт работать, когда меняешь компилятор/архитектуру.

  как чинят: счётчик целочисленный (for (uint64_t i = 0; i < n; ++i) { x = ... }),
  либо шаг, заведомо больший ulp, либо сравнение не с пределом, а по числу шагов.
